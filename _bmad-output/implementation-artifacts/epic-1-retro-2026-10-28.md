### Cross-story defects (no single session saw both sides)

**F1. Centres without coordinates are silently missing from search. [live]**
- **What happens:** Story 1.4 left 8 centres without coordinates: `muenchner-vhs-gmbh`, `bayerisches-rotes-kreuz`, `vhs-der-gemeinden-im-landkreis-roth`, `vhs-fichtelgebirge`, `vhs-kaufering`, `vhs-kreis-kronach-e-v`, `volkshochschule-eching-e-v` and `volkshochschule-kitzingen`.
- **How it happened:** 1.4 recorded as a residual risk that these "will not appear in distance searches" (spec-1-4, Residual risks). Story 1.8 then chose to skip them (spec-1-8, Design Notes, "Centres without coordinates are left out"). The skip is at `web/src/search/search.ts:269`.
- **What the user sees:** nothing tells them anything is missing.
  - Kitzingen at 10 km and Kronach at 10 km both show "No test centres within 10 km.", but both towns have a VHS test centre.
  - München at 20 km lists 14 centres, without Münchner Volkshochschule.
- **Requirements broken:** FR2 ("every directory centre within the radius"), NFR5 ("a gap must never read as nothing available"), and the intent of Story 1.3 ("no centre near me is missing").
- **Epic 2 risk:** About lists these centres today only because every centre is `not_checked` (`web/src/data/snapshot.ts:16-19`). Once Epic 2 covers one of them, it disappears from every page.
- **Sources:** all three reviewers (adversarial #1/#7, edge-case, verification-gap F2).
- **Disposition:** fix now.

**F2. "Bavaria only" is shown for a Bavarian town. [live]**
- **What happens:** "Lindau" shows "Error: This site covers Bavaria only". "88131 Lindau" shows "We don't know this place".
- **Why:**
  - The place table holds the Bavarian row as "Lindau (Bodensee)" and also has a bare "Lindau" in Schleswig-Holstein.
  - `resolvePlace` returns `outside_bavaria` on the bare exact match before the suggestion path runs (`web/src/search/search.ts:199-210`, `:296-298`).
  - The qualified form needs the name to match exactly (`:190-198`).
- **Who is affected:** the Lindau centre (`vhs-lindau`) can't be reached by its town name.
- **Likely to get worse:** after 1.11 adds the other states, Landsberg, Pfaffenhofen, Weiden and Neuburg are likely to collide the same way. This is not confirmed yet, because those rows are not in the file.
- **Requirement broken:** FR27.
- **Sources:** adversarial #3, edge-case.
- **Disposition:** fix now.

**F3. Non-Bavarian cities silently search a different Bavarian town. [live]**
- **What happens:** "Essen" searches Essenbach, "Hamm" searches Hammelburg, "Siegen" searches Siegenburg, and "Halle" searches Hallerndorf. Both the field and the shared link are rewritten to the Bavarian name.
- **Why:** this is Story 1.5's partial table (`complete:false`, 13 states missing) combined with Story 1.9's "one suggestion → search it" rule (`web/src/search/search.ts:296-304`).
- **What the specs assumed:** Story 1.8 accepted only "Berlin gets not found" for the partial table and said "Nothing in the code needs to change". 1.9 made the outcome worse. Nothing in `web/` reads `complete` or `missing`, though the `placesSchema` comment (`shared/places.ts:94-99`) says search must treat absent states as unknown.
- **1.11 will not fully fix it:** "Halle (Saale)" will never match a bare "Halle" exactly.
- **Requirements broken:** FR27 and FR25.
- **Sources:** all three reviewers.
- **Disposition:** fix now.

**F4. The epic's ordering rule was written down but not enforced.**
- **The rule:** `epics.md:156` and Story 1.11 say 1.11 "must land before Story 1.8 ships the 'Bavaria only' error and before Story 1.10".
- **What happened:** 1.8 and 1.9 shipped first, and every push to `main` deploys (`pipeline.yml`). The 1.8 review rejected this as "documented dependency … recorded as a residual risk" (spec-1-8 triage, IA row).
- **Result:** F2 and F3 are live.
- **Disposition:** process lesson (P1).

**F5. Setting coordinates by hand, the documented fix for F1, fails `npm test` and blocks publishing.**
- **The documented fix:** `tools/geocode.ts:9` and the 1.4 residual risks say that coordinates set by hand are supported.
- **The test:** `tests/directory.test.ts:204` requires a cache record matching every non-null coordinate.
- **The block:** `pipeline.yml` runs `npm test` before `npm run pipeline`.
- **Source:** adversarial #2, confirmed in the source.
- **Disposition:** fix now, together with F1.

**F6. Changes to `places.json` skip CI.**
- **The rule:** `ci.yml:6-12` ignores `data/public/**` as data owned by the bot (Story 1.1).
- **The conflict:** Story 1.5 put a hand-built, operator-committed `places.json` there. Stories 1.8 and 1.9 added strict committed-data tests against it.
- **Result:** Story 1.11's commit, which changes only data, would get no PR checks. Its first test run would be the publish job on `main`, where a failure blocks every deploy.
- **Source:** adversarial #5, confirmed in the source.
- **Disposition:** fix now, before 1.11.

**F7. A committed-data test is close to failing on a routine data change.**
- **The test:** `tests/search.test.ts:415-424` picks the town with the most centres within 40 km, then expects `found`.
- **The risk:** Jetzendorf has 26 centres in range and Eching has 25. Eching is ambiguous, so it resolves to "several". It sorts first if the two tie.
- **Status:** fragile, not broken.
- **Sources:** adversarial #6, edge-case.
- **Disposition:** fix now (low, small change).
